# Rust shown-memory projection

The Rust renderer follows the operator redesign recorded in
`docs/designs/memory-s3-projection.md`. The retired algorithm rebuilt a session's
memory view from canonical rows while subtracting deferred operations; Rust no
longer uses that reconstruction. A SOFT refresh may rewrite the delta block
(m[1]) while keeping the baseline block (m[0]) and its image frozen. Its memory
bytes depend only on previously shown state and its own immutable agent fragments.
Automated and foreign writes wait for an independently required HARD rebuild.

## Ownership and rendering

The applied tuple is `ModuleMeta.memory_projection` in store.db. Its text manifest,
captured row revisions, immutable metadata, profile, processed fragment watermark,
committed full/marker/aggregate fragments and baseline hash commit with the frozen
text/image pair under the existing cache generation CAS. Store migration 69 fences
older binaries that would otherwise drop the new JSON field on a metadata rewrite.
It adds no second cache table or cross-database transaction. The move inventory
ships the opaque cache meta and preserves the context.db fragment IDs.

Canonical mutations and their pre-rendered fragments commit in context.db first.
Rust's fragment namespace is `ck-mc`; identical host session names cannot cause it
to consume a TypeScript fragment from another harness. Explicit search and the
one-time hint producer compare current complete prose with the shown manifest;
an old revision, cue, marker or unknown legacy manifest does not suppress a hit.
Failure to load a visibility manifest disables suppression.

SOFT preserves committed fragments, uses 25% of the configured memory text
budget for corrections (the same allowance as TS/Pi), a
40-full-line limit, reserved marker budget and final aggregate line. Memory updates
are excluded from the independent pressure calculation. A real HARD captures
canonical rows/revisions and the fragment watermark together, then resets the
fragment ledger. A marker-only HARD uses applied memory/profile and scores and
the frozen image. If independent content is unchanged, it commits markers only,
preserving the complete prior pair and its tuple. Same-revision external SQL prose
repair and workspace/privacy invalidations remain stronger safety inputs.

## Departures from the original campaign specification

- There is no adoption-class scan, projected live/deferred operation pool,
  A1/A2/A3 rebase, additive admission ledger, or hole-bearing mutation cursor.
  Neither foreign nor automated changes reach SOFT. Only own agent fragments do.
- Automated cue correction does not ride SOFT. An explicit own agent operation
  can show its full correction or a stale marker, even for an image-only memory;
  the frozen image is never regenerated by that SOFT.
- Search returns unlabelled current text, as TS/Pi do, not revision/adoption labels.
- The cached pair already owns its bytes and image. The projection binds that
  pair by its m0 hash rather than duplicating all bytes in a second snapshot table.
- Rust currently receives a capability-gated, pre-rendered mural from the host,
  without a source revision manifest. This slice freezes that artifact in marker
  probes and SOFT/defer. It cannot prove a host image and Rust-selected canonical
  text were produced from one cross-process read snapshot; adding such a host wire
  contract requires changes in the host TypeScript adapters, not just these Rust
  crates. Unknown cues never hide full text.
- Dashboard approval/undo routing remains in the dashboard slice. No dashboard
  epoch setter is introduced here. Rust agent operations keep existing mutation
  rows for compatibility; the SOFT renderer never reads those rows.

The shared golden is generated by the production TS/Pi composer and consumed by
Rust. It includes fixed-seed SOFT/defer/HARD sequences and exact full, marker and
aggregate bytes. Rust integration-level unit fixtures separately exercise cache
restart, CAS loss, marker-only versus natural HARD and canonical-search visibility.
